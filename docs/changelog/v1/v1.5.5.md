# vitest-runner v1.5.5 Changelog

**Release Date**: October 2026
**Release Type**: Patch
**Branch**: `next` → `master`

---

## Overview

This release fixes a startup failure with Vitest 5's on-disk module cache. Right after a lockfile change, parallel workers could fail with `ENOTEMPTY` because they all tried to delete the same cache directory at once, and in a workspace whose packages have different lockfiles, those packages kept clearing each other's cache. The runner now gives each package its own cache directory and does Vitest's lockfile check once per run, before the workers start ([#101](https://github.com/CLDMV/vitest-runner/pull/101), fixes [#100](https://github.com/CLDMV/vitest-runner/issues/100)).

The fix comes with a new `fsModuleCachePath` option for `run()`, so this patch release adds API. The published package also gains one file, `fs-cache-helper.mjs`, next to `dist/index.mjs` and `bin/vitest-runner.mjs`. On Vitest versions before 5 nothing changes.

The entry sources are also renamed to `src/index.mjs` and `src/index.cjs` ([#102](https://github.com/CLDMV/vitest-runner/pull/102), closes [#98](https://github.com/CLDMV/vitest-runner/issues/98)). The published `dist/index.mjs` and `dist/index.cjs` keep their names and behaviour.

## 🐛 Bug Fixes

### Parallel workers no longer race on Vitest's module cache ([#101](https://github.com/CLDMV/vitest-runner/pull/101))

Vitest 5 caches transformed modules on disk (`fsModuleCache`, on by default in Vitest 5.0.5). By default the cache lives in `node_modules/.vitest-cache` at the workspace root, shared by every package, and each Vitest process deletes the whole directory on startup when the lockfile no longer matches the one the cache was written for. The runner starts several Vitest processes at once (`--workers`, default 4), so the first run after `npm install` or `pnpm install` could fail in some of them:

```text
⎯⎯⎯⎯⎯⎯⎯ Startup Error ⎯⎯⎯⎯⎯⎯⎯⎯
[Error: ENOTEMPTY: directory not empty, rmdir '…/node_modules/.vitest-cache']
```

A rerun always passed. Packages in one workspace with their own lockfile had a second problem: each package compared the shared cache with a different lockfile, so every switch between them cleared the whole cache even when nothing had been installed.

Before any test file runs, the runner now starts one short helper process. It loads the project's Vitest config, the root and every project, with the same arguments the workers get, and:

- **picks a cache per package**: when the cache is on and nothing sets a path, every Vitest child gets `--fsModuleCachePath=<cwd>/node_modules/.vitest-cache`;
- **checks the lockfile once**: when files will run in parallel, it starts Vitest once, which clears a stale cache, and exits before the workers start.

A path set anywhere in the resolved config, including a project's own config or a file pulled in with `mergeConfig`, is kept. If the helper fails or takes longer than a minute, the runner prints a warning and runs the files as before. On Vitest versions before 5, which have no top-level `fsModuleCachePath`, the helper is not started at all.

## ✨ Features

### `fsModuleCachePath` option for `run()` ([#101](https://github.com/CLDMV/vitest-runner/pull/101))

Sets the Vitest module cache directory for every child, relative to `cwd` or absolute. The path is chosen in this order:

1. a `--fsModuleCachePath` passthrough argument;
2. the `fsModuleCachePath` option (`false` adds nothing and leaves Vitest's own setting in place);
3. `fsModuleCachePath` set anywhere in the resolved Vitest config;
4. `<cwd>/node_modules/.vitest-cache`.

There is no new CLI flag. From the command line, pass Vitest's own `--fsModuleCachePath` through.

The root entry also exports `prepareFsModuleCache()`, the step `run()` uses, and `DEFAULT_FS_MODULE_CACHE_DIR`, for scripts that start Vitest processes themselves.

## 🔧 Internal

### Entry sources renamed to `src/index.mjs` and `src/index.cjs` ([#102](https://github.com/CLDMV/vitest-runner/pull/102))

The CommonJS entry was written as `src/cjs-shim.cjs` and required `./index.mjs`, a file that only existed once the build had copied both into `dist/`. With the ES module entry renamed to `src/index.mjs` and the CommonJS entry to `src/index.cjs`, that `require` resolves the same way in `src/` and `dist/`, so the CommonJS entry is now tested from source and counts towards coverage. `dist/index.cjs` is still a verbatim copy of the source file; only its comments changed.

The `vitest-runner-dev` export condition now points at `./src/index.mjs`. That only matters for a local checkout or workspace copy run with `--conditions=vitest-runner-dev`; `src/` is not published.

## Upgrade notes

- No breaking changes: a drop-in replacement for [v1.5.4](./v1.5.4.md).
- On Vitest 5 with the cache on, the cache moves from the workspace root into each package's own `node_modules/.vitest-cache`, so the first run after upgrading starts with an empty cache. The old shared directory at the workspace root is no longer used by the runner and can be deleted.
- Each run on Vitest 5 starts one extra short process before the first test file. It takes about half a second for a small config, more for configs with heavy plugins.
- To keep Vitest's own cache location, pass `fsModuleCachePath: false` to `run()`. To choose one, pass `--fsModuleCachePath <dir>` through on the command line.
